# 스터디 판정 개선 배포와 확인

## 배포 순서

1. 기존 커밋이 있는 체크아웃에서 `node scripts/verify-release-restore.mjs`를 실행한다. 격리 DB에서 구버전의 영어 인증과 사진 조회, 새 기록 보존, 백업 복원을 검증한다.
2. 머지 전에 Vercel **Production**에 Supabase의 직접 연결 또는 세션 풀러 연결을 설정한다. Supabase 통합에서 공급하는 `POSTGRES_URL_NON_POOLING` 또는 `POSTGRES_URL`이 있으면 사용한다. 직접 지정할 때에는 소유한 햄쮸터 객체를 변경할 수 있는 연결 주소를 `HAMSTER_MIGRATION_DATABASE_URL`에 저장한다. 자격 증명은 Vercel의 비밀 환경 변수 입력란에서 저장한다. 별도 루트 인증서가 필요한 직접 연결은 Supabase 프로젝트의 CA를 `HAMSTER_MIGRATION_CA_CERT`에 설정할 수 있다. 서버는 TLS 서버 인증서와 공개 Supabase 프로젝트 주소가 가리키는 DB를 확인한다. [Supabase 연결 안내](https://supabase.com/docs/guides/database/connecting-to-postgres)
3. `main` 머지로 시작하는 운영 빌드는 앱을 먼저 빌드한다. 성공하면 `202611230008`까지 운영하던 스키마를 확인하고 그 이후의 새 SQL 파일과 체크섬을 **한 트랜잭션**으로 적용한다. 첫 변경은 기존 풀이에 그때까지 표시되던 등급을 복사한다. 초대 신규 가입은 커밋 시점부터 승인을 거친다. 기존 계정·세션·확정 벌금은 보존된다. SQL 실패 시 해당 트랜잭션 전체가 취소된다. Vercel은 마지막으로 REST 스키마, 인증 설정, 적용 이력을 읽어 확인한 뒤 새 앱을 배포한다. 배포 실패 시 이전 앱이 계속 요청을 처리한다. 커밋 직후 연결 점검만 실패한 경우, 같은 커밋을 다시 배포하면 저장된 이력을 읽어 SQL 재적용을 건너뛴다.

   프리뷰 빌드는 운영 DDL을 실행하지 않는다. DB가 분리된 격리 시험은 `HAMSTER_TEST_DATABASE_URL`에 loopback 연결만 받아 `node scripts/migrate-release.mjs --local`로 같은 SQL과 실행기를 검증한다. Vercel Preview와 Production 각각의 읽기 확인 기준은 `/api/health?mode=ready`의 HTTP 200이다. `HAMSTER_EXPECTED_SUPABASE_HOST`에는 팀이 확인한 프로젝트 호스트를 별도로 지정할 수 있다. 운영용 DDL을 포함한 릴리스는 `main` 운영 빌드를 거쳐 배포한다.
4. 새 앱이 **운영으로 승격된 후** GitHub의 **Activate promoted study day worker**가 정식 도메인을 호출한다. 서버는 자기 커밋과 배포 주소가 저장소의 Vercel 봇이 남긴 Production 성공 기록에 일치하는지 대조한다. 검증된 승격 시각에 열려 있던 인증일을 최초 `nextDate`로 한 번 저장한다. 예를 들어 25일 03:59에 배포를 마치고 04:01에 콜백이 도착해도 24일부터 시작한다. 활성화 자체의 금액 쓰기는 0건이다. 재호출도 시작일을 이동시키지 않는다. Vercel Git 설정에서 `deployment_status` 이벤트를 사용하고, 워크플로가 실패하면 해당 실행을 재시도한다. 수동 복구가 필요한 경우 이전 마감을 확인한 운영자가 운영 `/api/cron/finalize`에 기존 Cron 자격 증명으로 POST해 현재 열린 인증일부터 시작할 수 있다. 프리뷰 점검은 읽기 전용 `/api/health?mode=ready`로 진행한다. 완료일 이후 늦게 수신한 풀이는 `hamster_late_solve_reviews`에 남는다. 기존 원장 수정과 과거 벌금 신규 부과는 금액 비교를 먼저 확인한 뒤 건별로 승인한다.
5. 조회 최적화 기본 설정은 `HAMSTER_PROGRESS_MODE=off`다. 적용할 스터디 ID를 `HAMSTER_PROGRESS_STUDIES`에 지정하고 `shadow`에서 기존·새 계산을 병행한다. 달력·미루기 결과가 일치하는지 확인한 뒤 같은 스터디에 `on`을 적용한다. 과거 자료 변경이나 첫 준비 때는 원본을 다시 읽는다. 과거 월에는 뒤늦은 보충 반영을 위해 그 달 이후의 기록도 필요하다.

## 장애 대응

- 달력에 표시된 `CAL-` 문의 번호로 서버 로그의 조회 단계와 연결할 수 있다. 계정명과 풀이 내용을 로그에 넣지 않는다.
- 한국 시각 04:05 마감, 08:10 GitHub 재처리, 08:20 마감 재실행 순서다. GitHub Actions의 **Study day close monitor**가 별도로 05:06·05:16·09:26에 확인한다. 05:05를 기준으로 전날의 마감이 끝나야 정상이다. 미시작, 진행 정체, 읽기·쓰기 실패를 구분한다. 실패 코드 `55000`은 접수 후 미처리된 GitHub 기록, `40001`은 계산 중 변경되어 재시도가 필요한 경우다. GitHub 예약 실행 및 담당자 통지의 실제 도착 시각은 운영에서 확인한다.
- 활성화 전 GET은 503으로 끝나며, 프리뷰의 마감 GET·POST는 차단된다. 계산 경로에 차이가 나면 해당 스터디를 대상에서 빼거나 `off`로 재배포한다. 구버전 화면을 복구할 때 새 마감 작업과 원장 보호를 유지한다. 배포 이후의 인증은 원본 DB에 남는다.

## 운영 측정

- `scripts/report-service.sql`은 최근 30일 모바일 폭에서 첫 달력·미루기의 성공 표본 수, 실패 수, p75 상한을 반환한다. 100ms 단위로 올림하고 각각 30건부터 판정한다. 최초 달력은 화면 반영 뒤, 미루기는 버튼을 누른 순간부터 서버 확인을 표시한 뒤까지 잰다. 백그라운드·프리뷰 표본은 제외한다. 목표는 각각 2,500ms와 1,000ms다. 재방문 캐시는 브라우저의 `hamster:calendar_warm` 성능 기록으로 확인한다.
- 앱에 저장되는 시간 자료는 날짜·동작·화면 폭 분류·성공 여부·시간 구간별 건수다. 다음 관측이 들어오면 35일을 벗어난 날짜를 정리한다. 같은 SQL에서 햄쮸터 테이블과 인덱스 크기를 따로 집계할 수 있다.
- 월 비용 보고는 같은 청구 기간의 Vercel 프로젝트별 호출·전송량, Supabase 프로젝트 청구액과 햄쮸터 테이블·사진 용량을 사용한다. 공유 컴퓨팅·전송량에서 서비스별 원가를 식별할 수 없는 부분은 추정 범위와 함께 표시한다.
- `node scripts/benchmark-progress.mjs`는 격리 DB에서 2명·20명, 30일·365일·730일을 비교한다. 여기서 읽기량은 DB가 앱에 반환한 행 수다. 실행 시간은 로컬 API 핸들러와 DB를 포함한다.
