# 2026-10-16

## 목표
Study별 설정 상한 N을 그대로 유지하면서, N일까지 미룬 뒤 N+1번째 날에는 가장 오래된 의무를 통째로 상환해야 다시 미룰 수 있도록 API와 달력 상태를 일치시킨다.

## 변경 내용
- `getPostponementStatus`로 허용 여부, 상한, 남은 날짜 수, 필요한 완전 상환 일수, 거부 사유를 함께 계산한다. 숫자 2를 하드코딩하거나 설정 화면의 0~7 범위를 축소하지 않는다.
- `GET /api/postponements?studyId=...`와 POST는 같은 서버 정책을 사용한다. POST는 클라이언트의 상한/진행률/허용 플래그를 신뢰하지 않는다.
- 달력 응답에 본인의 `todayPostponement`를 포함한다. 버튼은 이를 사용해 잠그며, 별도 최초 조회 없이 기존 달력 결과를 재사용한다. 명시적인 `상태 다시 확인`은 GET을 호출한다.
- 수동 등록, backfill, 규칙 변경으로 달력을 다시 읽으면 미루기 잠금도 갱신한다. POST 성공과 이미 신청된 날짜의 재요청을 구분한다.
- 마감은 Study Day에 연결된 실제 timestamp로 검사한다. 기본 23:59가 자정 이후 다시 열리지 않고, 새벽 마감 설정은 다음 날 04:00 전까지로 해석한다. 처리 도중 04:00을 넘긴 요청과 이전 날짜 화면의 POST도 거부한다.
- 과거 월의 달력을 조회하더라도 오늘까지 상환 기록을 계산한다. `resolvedOn`을 응답에 포함해 보충 완료일을 표시하며 미루기 신청 이력과 확정 벌금은 보존한다.
- 진행 상태와 달력 계산에 필요한 이력은 안정된 정렬/페이지 조회로 끝까지 읽는다. 조회 실패와 누락된 관계를 0건으로 간주하지 않고 오류로 응답한다.
- 신규 migration으로 미루기 직접 INSERT 경로를 닫고 서버 API에서만 저장하도록 한다. 설정/풀이/벌금 데이터와 타 앱 객체는 변경하지 않는다.

## 변경 이유
기존의 순수 backlog 비교는 이미 `backlogCount <= N`이었다. 그 조건만 다시 추가하거나 상한을 2로 강제하는 것은 해결책이 아니다. 이번 점검에서는 달력의 월말 조회 경계, 직접 INSERT 허용 정책, 자정 뒤 재개되는 시각 비교, 페이지 누락과 UI의 무조건 활성 버튼을 보강했다.

동료의 실제 요청 로그와 운영 DB는 조회하지 않았으므로 어느 경로가 해당 사례의 직접 원인인지는 확정하지 않는다. 과거에 이미 저장된 초과 미루기를 임의로 삭제하지 않는다.

## 검증
- 실제 Next.js GET/POST handler, context loader, FIFO 엔진을 호출한다. 인증/DB I/O만 메모리 테스트 더블로 대체한다.
- 상한 1~7 각각 N일까지 성공, N+1번째 409와 INSERT 없음, 0.5 상환 거부, 1일치 완전 상환 뒤 허용, 상한 0을 확인한다.
- 재요청/동시 요청의 중복 방지, 비회원/타 사용자, 위조된 클라이언트 허용 값, 조회/저장 실패를 확인한다.
- 유효 규칙 버전, 23:59/00:00/04:00 경계, 조회 도중 날짜 변경을 확인한다.
- 1,000행 이후의 상환과 더 작은 프로젝트 응답 제한, 중간 페이지 실패를 확인한다.
- 월 경계 상환, 확정 벌금 보존, 실제 React 컴포넌트의 잠긴 버튼/사유 렌더링을 확인한다.
- Repository Harness, 전체 `npm test`, 최종 커밋 CI와 Vercel 상태는 PR #22의 검증란에 결과를 기록한다.

## 운영 적용
1. `supabase/migrations/202610160001_guard_postponement_writes.sql`을 SQL Editor에서 실행한다.
2. CI와 Preview 확인 후 PR #22를 squash merge한다.
3. Production 배포 후 달력을 새로고침한다.

이 migration은 hamster 미루기의 직접 INSERT 권한만 제한한다. 기존 API도 service_role을 사용하므로 코드 배포 전 선적용할 수 있다. 기존 설정, 미루기 이력, 벌금 보정 작업은 없다.

## 남은 점
- 운영 DB migration 실행과 실제 계정/모바일에서의 확인은 수행하지 않았다.
- 기존에 잘못 저장된 미루기는 별도 승인 없이 자동 삭제하거나 벌금을 소급 수정하지 않는다.
- 조회/쓰기와 다른 요청의 규칙 변경을 하나의 DB 트랜잭션으로 묶지는 않는다. 같은 날짜 중복 쓰기는 기존 unique constraint가 막으며, 서버는 요청마다 현재 이력과 유효 규칙을 다시 조회한다.
