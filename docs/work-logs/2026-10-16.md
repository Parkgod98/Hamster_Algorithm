# 2026-10-16

## 목표
Study별 설정 상한 N을 그대로 유지하면서, N일까지 미룬 뒤 N+1번째 날에는 가장 오래된 의무를 통째로 상환해야 다시 미룰 수 있도록 API와 달력 상태를 일치시킨다.

## 변경 내용
- `getPostponementStatus`로 허용 여부, 상한, 남은 날짜 수, 필요한 완전 상환 일수, 거부 사유를 함께 계산한다. 숫자 2를 하드코딩하거나 설정 화면의 0~7 범위를 축소하지 않는다.
- `GET /api/postponements?studyId=...`와 POST는 같은 서버 정책을 사용한다. POST는 클라이언트의 상한/진행률/허용 플래그를 신뢰하지 않는다.
- 달력 응답에 본인의 `todayPostponement`를 포함한다. 버튼은 이를 사용해 잠그며, 별도 최초 조회 없이 기존 달력 결과를 재사용한다. 명시적인 `상태 다시 확인`은 GET을 호출한다.
- 수동 등록, backfill, 규칙 변경으로 달력을 다시 읽으면 미루기 잠금도 갱신한다. POST 성공과 이미 신청된 날짜의 재요청을 구분한다.
- 마감은 Study Day에 연결된 실제 timestamp로 검사한다. 기본 23:59가 자정 이후 다시 열리지 않고, 새벽 마감 설정은 다음 날 04:00 전까지로 해석한다. 처리 도중 04:00을 넘긴 요청과 이전 날짜 화면의 POST도 거부한다.
- 과거 월의 달력을 조회하더라도 오늘까지 상환 기록을 계산한다. `resolvedOn`을 응답에 포함해 보충 완료일을 표시하며 미루기 신청 이력과 확정 벌금은 보존한다.
- 진행 상태와 달력 계산에 필요한 이력은 안정된 정렬/페이지 조회로 끝까지 읽는다. 조회 실패와 누락된 관계를 0건으로 간주하지 않고 오류로 응답한다.
- 신규 migration으로 미루기 직접 INSERT 경로를 닫고 서버 API에서만 저장하도록 한다. 설정/풀이/벌금 데이터와 타 앱 객체는 변경하지 않는다.

## 변경 이유
기존의 순수 backlog 비교는 이미 `backlogCount <= N`이었다. 그 조건만 다시 추가하거나 상한을 2로 강제하는 것은 해결책이 아니다. 초기 점검에서는 달력의 월말 조회 경계, 직접 INSERT 허용 정책, 자정 뒤 재개되는 시각 비교, 페이지 누락과 UI의 무조건 활성 버튼을 보강했다.

초기 점검 당시에는 운영 DB/요청 로그가 없어 직접 원인을 확정하지 않았다. 이후 제공된 진단 자료와 Max Rows 확인 결과는 아래 추가 작업에 기록한다. 과거에 이미 저장된 초과 미루기를 임의로 삭제하지 않는다.

## 검증
- 실제 Next.js GET/POST handler, context loader, FIFO 엔진을 호출한다. 인증/DB I/O만 메모리 테스트 더블로 대체한다.
- 상한 1~7 각각 N일까지 성공, N+1번째 409와 INSERT 없음, 0.5 상환 거부, 1일치 완전 상환 뒤 허용, 상한 0을 확인한다.
- 재요청/동시 요청의 중복 방지, 비회원/타 사용자, 위조된 클라이언트 허용 값, 조회/저장 실패를 확인한다.
- 유효 규칙 버전, 23:59/00:00/04:00 경계, 조회 도중 날짜 변경을 확인한다.
- 1,000행 이후의 상환과 더 작은 프로젝트 응답 제한, 중간 페이지 실패를 확인한다.
- 월 경계 상환, 확정 벌금 보존, 실제 React 컴포넌트의 잠긴 버튼/사유 렌더링을 확인한다.
- Repository Harness, 전체 `npm test`, 최종 커밋 CI와 Vercel 상태는 PR #22의 검증란에 결과를 기록한다.

## 운영 적용
1. `supabase/migrations/202610160001_guard_postponement_writes.sql`을 SQL Editor에서 실행한다.
2. 최종 HEAD의 CI와 Preview 확인 후 PR #22를 squash merge한다.
3. Production 배포 후 달력을 새로고침한다.

이 migration은 hamster 미루기의 직접 INSERT 권한만 제한한다. 기존 API도 service_role을 사용하므로 코드 배포 전 선적용할 수 있다. 기존 설정, 미루기 이력, 벌금 보정 작업은 없다.

## 남은 점
- 운영 DB migration 실행과 실제 계정/모바일에서의 확인은 수행하지 않았다.
- 기존에 잘못 저장된 미루기는 별도 승인 없이 자동 삭제하거나 벌금을 소급 수정하지 않는다.
- 조회/쓰기와 다른 요청의 규칙 변경을 하나의 DB 트랜잭션으로 묶지는 않는다. 같은 날짜 중복 쓰기는 기존 unique constraint가 막으며, 서버는 요청마다 현재 이력과 유효 규칙을 다시 조회한다.

## 추가 작업: 조회 누락 원인과 월별 캐시

### 목표
최신 풀이 누락을 해결하면서 달력 월 왕복 때 동일 조회를 반복하지 않도록 한다. 화면은 선택 월의 상세만 받고, 월을 넘는 FIFO 의무 계산은 유지한다.

### 확인한 원인
운영자가 제공한 진단 결과에서 누락된 두 풀이가 GitHub source로 당시 정상 저장되어 있었고 webhook 처리 기록도 있었다. 스터디 전체는 1,004건, 해당 두 건 앞에는 각각 1,002건과 1,003건이 있었다. 운영자가 Max Rows=1,000을 확인했다. 기존 달력의 오래된 순서 단일 조회는 마지막 기록을 반환받지 못한다. 이번 사례는 백준 난이도나 webhook 저장 누락으로 설명할 상황이 아니다. 원본 사용자 ID/전달 ID/로그는 저장소에 남기지 않는다.

### 변경 내용
- 달력 응답을 로그인 사용자/Study/월별 메모리 캐시로 5분 재사용한다. 최대 12개 월까지만 보관한다.
- 유효한 월로 돌아오면 HTTP를 생략한다. 만료된 월은 이전 결과를 보여주면서 조회하며 갱신 중/실패를 표시한다. 실패한 갱신을 새 성공 캐시로 기록하지 않는다.
- 같은 키의 동시 요청은 공유한다. 다른 월의 진행 요청은 취소하고 요청 순번 검사로 늦은 응답이 화면을 덮지 못하게 한다.
- 수동 인증/미루기/backfill/규칙 저장 후에는 해당 Study의 월 캐시 전체를 무효화한다. 수동 새로고침 버튼은 성장 통계 캐시도 갱신한다.
- 04:00, 미루기 마감, 앱 복귀에서 캐시 유효성을 검사한다. 로그아웃/계정 변경/화면 종료는 캐시와 진행 요청을 폐기한다. Service Worker/API HTTP 캐시와 토큰 저장은 추가하지 않는다.
- 서버는 참여 이후 진행 판정용 최소 필드(사용자, 시각, 플랫폼, 난이도)와 선택 월의 상세(제목, 문제 번호 등)를 나눠 조회한다. 현재 멤버들 중 가장 이른 참여일 전 기록은 DB에서 제외하며, 더 늦게 가입한 멤버는 자신의 참여일 전 기록을 판정에서 제외한다.
- 선택 월 밖의 문제 제목은 읽지 않는다. 과거 월 조회도 오늘까지의 최소 이력으로 상환을 계산하므로 완료 아이콘과 확정 벌금을 보존한다.
- 성장 통계도 최근 3개월 기간 필터를 유지하면서 모든 페이지를 읽고 중간 페이지 오류를 실패로 반환한다.
- Max Rows, 설정값, 원본 이력과 기존 migration은 변경하지 않는다. 캐시/조회 보강을 위한 별도 migration은 없다.

### 검증
- 캐시 단위 테스트: 월 왕복, 5분 TTL, 04:00/마감 경계, 계정/Study 분리, LRU 12개 제한, mutation과 로그아웃 무효화, 중복 요청 공유, 늦은 응답 차단, 오류 재시도.
- 실제 API 핸들러 테스트: 1,004건 마지막 두 풀이를 달력/통계에 포함, Max Rows 1,000과 100, 기간/선택 필드 확인, 참여 전 이력 제외, 미래 월, 다른 Study 대상 차단, 중간 페이지 실패.
- 기존 63개 테스트를 삭제하지 않는다. 최종 테스트 건수와 Harness 결과는 PR에 기록한다.

### 남은 점과 선택한 범위
- 페이지 조회는 DB snapshot 트랜잭션이 아니다. 별도 집계 테이블/Redis/worker를 도입하지 않았다.
- 캐시가 없거나 만료되어 서버를 호출하면 진행 판정용 과거 최소 이력은 여전히 재계산한다. 모든 DB 조회가 해당 월로만 제한된다고 주장하지 않는다.
- 상세와 진행 쿼리를 분리하므로 첫 요청의 SQL 횟수 자체가 항상 줄어드는 것은 아니다. 반복 월 요청 제거와 불필요한 상세 전송 축소가 목표다. 운영 지연시간/비용은 계측하지 않았다.
- 자동 GitHub 풀이의 화면 반영은 월/탭 이동, 앱 복귀 시 TTL 재검사 또는 새로고침이다. 앱을 계속 열어두었을 때 5분마다 polling하지 않으며 실시간 반영을 보장하지 않는다.
- 네트워크 제한으로 작업 컨테이너에서 전체 저장소 clone/npm install은 불가능했다. 캐시 단위 테스트는 격리된 로컬 사본에서 실행했고, 전체 저장소 Harness/테스트/빌드는 GitHub CI에서 검증한다.
- 실제 브라우저/모바일 E2E와 Production 배포 후 두 풀이 표시 확인은 별도로 필요하다.
