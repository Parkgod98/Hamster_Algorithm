## P0/P1 런타임 효율화

### 목표
서비스 동작과 FIFO backlog 규칙을 유지하면서 반복 DB 조회, 전체 이력 스캔, 중복 계산, 순차 I/O를 줄입니다.

### 변경 내용
- 풀이 성장 통계에 사용자/Study/월 단위 5분 메모리 cache를 적용하고 수동 인증/backfill 성공 시 무효화합니다.
- 성장 통계 API는 전체 풀이 이력이 아니라 선택 월을 포함한 최근 3개월 Study Day 범위만 조회합니다.
- 진행 상태 계산용 Study context를 공통화해 미루기, GitHub webhook, 수동 인증의 중복 조회를 줄였습니다.
- completion Push의 before/after 판정은 기존 데이터를 다시 조회하지 않고 같은 context에 새 풀이를 추가해 재계산합니다.
- reminder cron은 Push 필요 가능성이 있는 사용자만 선별하고 Study 단위로 진행 상태 데이터를 한 번 읽습니다.
- 이미 현재 모든 subscription에 reminder가 성공했거나 subscription이 없거나 reminder가 꺼진 사용자는 progress 계산 전에 제외합니다.
- FIFO progress engine은 oldest unresolved pointer와 backlog counter를 사용해 날짜마다 과거 obligation 전체를 다시 훑지 않습니다.
- Dashboard는 평가 종료 시점 이후 submission/postponement를 읽지 않고 penalty는 선택 월만 조회합니다.
- Dashboard와 finalize cron은 사용자별 Map으로 데이터를 한 번 그룹핑해 멤버마다 전체 배열을 재순회하지 않습니다.
- finalize cron은 대상 날짜의 기존 벌금을 한 번에 preload해 멤버별 존재 확인 query를 제거했습니다.
- Repository backfill은 commit detail 최대 8개 동시 조회와 problem/submission batch 저장으로 변경했습니다.
- DB schema와 migration은 변경하지 않았습니다.

### 변경 이유
사용자가 늘거나 풀이 이력이 누적될수록 같은 데이터의 반복 조회와 멤버별 전체 배열 재순회가 Supabase 읽기량과 Vercel 함수 실행시간을 불필요하게 증가시키는 구조였습니다. 현재 규모에 맞는 메모리 cache, bounded query, batch I/O만 적용하고 별도 cache server나 집계 DB는 도입하지 않았습니다.

### 검증
- Repository Harness 전체
- FIFO backlog 회귀 테스트
- 730일 장기 timeline 테스트
- Asia/Seoul 04:00 Study Day timestamp boundary 테스트
- PR CI
- Vercel Preview

### 남은 점
- 운영 데이터 규모가 크게 증가하기 전까지 Redis, materialized view, progress snapshot 영구 저장은 도입하지 않습니다.
