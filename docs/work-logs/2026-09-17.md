# 2026-09-17

## 목표
모바일 Web Push에서 실제 미수신이 발생해도 중복 방지 상태 때문에 영구 누락되지 않도록 전송 신뢰성, 기기 구독 판정, reminder 스케줄 관측성을 보강합니다.

## 점검 결과
- 기존 구현은 실제 Push 성공 전에 사용자 단위 delivery row를 먼저 생성해 전송 실패도 중복으로 잠길 수 있었습니다.
- `알림 켜짐`은 현재 기기가 아니라 사용자 계정에 subscription이 하나라도 있으면 켜진 것으로 표시했습니다.
- GitHub webhook/수동 인증 API가 Push 처리 오류의 영향을 받을 수 있었습니다.
- reminder cron은 전송 결과를 `sent`만 집계해 실패 원인과 만료 subscription을 구분하기 어려웠습니다.
- Vercel Hobby Cron의 시간 정밀도를 고려한 backup 실행과 서버 측 시간 창 방어가 없었습니다.

## 변경 내용
- 신규 migration으로 delivery를 subscription 단위 `pending/sent/failed` 상태 추적으로 전환했습니다.
- 실제 Push 성공 후에만 `sent_at`을 기록하고 실패 상태는 재시도할 수 있게 했습니다.
- 404/410 subscription 정리, 일시 실패 1회 즉시 재시도, stale pending 재시도를 추가했습니다.
- delivery claim에 attempt count 조건을 추가해 동시 실행 중복 가능성을 낮췄습니다.
- 현재 브라우저 endpoint를 API에 전달해 현재 기기 기준으로 알림 설정 상태를 표시합니다.
- VAPID public key 변경을 감지하면 기존 subscription을 해제하고 재구독할 수 있게 했습니다.
- 현재 기기로 실제 Push를 보내는 `테스트 알림 보내기` API/UI를 추가했습니다.
- Push 실패가 이미 저장된 GitHub 자동 인증 또는 수동 인증 응답을 실패시키지 않도록 격리했습니다.
- reminder cron에 시간 창 검사와 멤버별 오류 격리, 상세 summary 로그를 추가했습니다.
- `30 14 * * *` primary와 `0 15 * * *` backup reminder를 함께 등록해 Hobby Cron 지연 시 재시도 기회를 확보했습니다.

## 미루기 backlog FIFO 재설계

### 확인된 문제
- 기존 `evaluateTimelineByDay`는 `postponed=true`인 날짜를 인증 의무에서 사실상 건너뛰었습니다.
- 그 결과 9/15, 9/16을 미룬 사용자가 9/17에 1일치만 풀어도 9/17만 완료되고 과거 두 날짜는 영구적으로 미루기 상태에 남았습니다.
- 실제 햄쮸터 규칙은 미루기가 면제가 아니라 이월이므로 도메인 모델이 잘못되어 있었습니다.

### 확정한 규칙
- 매 Study Day마다 1일치 obligation이 생기며 미루기는 이 obligation을 삭제하지 않습니다.
- 모든 풀이 credit은 가장 오래된 미해결 obligation부터 FIFO로 상환합니다.
- 부분 credit은 잔여량을 줄이지만 1일치를 완전히 해결하기 전에는 하루 상환으로 인정하지 않습니다.
- 기본 최대 미루기 2에서는 현재 미해결 obligation이 2개 이하일 때만 오늘 미루기가 가능합니다. 3개가 밀렸다면 최소 1개를 완전히 해결해야 합니다.
- backlog를 전부 갚은 뒤 남은 credit만 선풀이에 사용합니다.
- 미루기 없이 마감되면 미해결 obligation 1/2/3개 이상에 따라 1/2/3회 벌금을 적용하고 3회에서 cap합니다.
- 한번 확정된 벌금은 이후 과거 obligation을 갚아도 유지합니다.

### 구현
- `src/lib/progress.ts`를 obligation backlog FIFO 엔진으로 변경했습니다.
- `memberProgressSnapshot`을 추가해 Push와 미루기 API가 같은 계산 결과를 사용하게 했습니다.
- 미루기 API는 날짜 연속 횟수가 아니라 현재 backlog 개수와 완전 상환 여부로 허용 여부를 판단합니다.
- finalize cron은 마감 시 backlog 개수를 벌금 단계로 사용하며 이미 확정된 penalty row를 덮어쓰지 않습니다.
- 3일 초과 backlog는 3회 최고 벌금으로 제한합니다.
- 확정 시나리오에 대한 `postponement-backlog.test.mjs` 회귀 테스트를 추가했습니다.
- DB schema 변경은 없습니다.

### 검증
PR CI에서 Repository Harness 전체와 신규 backlog 회귀 테스트를 확인합니다.
